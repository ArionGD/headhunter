01

What's Already Built

Out of the box, confirmed against ARCHITECTURE.md and the dependency manifests — none of this needs to be coded.

Confirmed CRM via Django Admin

No custom CRM to build. Leads, Deals, Campaigns, Mailboxes, and Tasks are all standard Django models, browsable and editable straight from /admin/.

Confirmed Bayesian GP qualification

A scikit-learn Gaussian Process Regressor (ConstantKernel × RBF) scores each lead's 384-dim FastEmbed embedding, with BALD active learning choosing which unlabeled lead to send to the LLM next.

Confirmed BetterContact resolution

One API key powers both stages: Lead Finder discovery and paid work-email resolution. Billed per verified hit — a miss costs nothing.

Confirmed Agentic email loop

Persistent Task model drives find_email → collect_email → follow_up → email. IMAP reply-reading lets the agent decide send / wait / mark-complete on live threads.

Confirmed Own task queue, no Celery

No Redis, no broker. A DB-backed queue on the Task model, driven by manage.py rundaemon — one process, one worker loop in core/daemon.py.

Confirmed Warm-safe sending

Per-mailbox daily_limit (default 30/day), active-hours window (9am–7pm by default), and human-rhythm burst/break pacing (45–65 min bursts, 10–20 min breaks).

The full lifecycle it runs for you

Every discovered lead moves through one state machine, entirely automated once a campaign is live:

Lead discovered → embedded → LLM qualify decision ↳ QUALIFIED (LLM said yes, no email yet) ↳ GP score clears 0.9 confidence bar → READY_TO_FIND_EMAIL ↳ BetterContact lookup in flight → FINDING_EMAIL ↳ hit → READY_TO_EMAIL / miss → FAILED (no email) ↳ opener sent → EMAILED ↳ IMAP reply watched, agent replies → COMPLETED or FAILED

You are not building any of the above. Your job is entirely upstream of it: telling the system who to find and what to say — which is Section 04.

03

The Gap — And How to Work Around It

This is the one place your brief and the tool's real architecture diverge. Read this before you touch the onboarding wizard.

Why this matters

The Clause filter system that Lead Finder queries run through only accepts (family, value) pairs from a provider-defined family list — job title, seniority tier, department, function, free-text company/location strings. Numeric ranges of any kind (age, tenure, company size) were explicitly evaluated by the maintainers and removed from earlier filter families because they didn't verifiably steer results. There's no version of this you're missing in a settings screen — it isn't there to configure.

What to do instead

  • Drop "35–50" and "10+ years" as filters. Push them into campaign_target as qualifying prose instead — the LLM qualifier reads that text on every candidate and can reject anyone whose visible title/seniority signal doesn't imply a senior, established professional, even though it can't check a birth year.
  • Let job title carry the seniority weight. "VP", "Director", and "Senior Manager" already imply years-of-experience in most corporate contexts — lean on title + seniority-tier as your real proxy for tenure, since that's the filter family that's actually provider-verified to work.
  • Use country_code: IN, then keyword-narrow. Set the campaign's country to India, and put "Chennai", "Tamil Nadu" as free-text interest/location keywords in campaign_target — treat it as a soft nudge the LLM and discovery pass will try, not a guaranteed city filter. Expect leakage to other Indian metros and plan to manually reject those in the CRM.
  • Budget for a manual QUALIFIED-stage review pass. Since city and age can't be gated upstream, your highest-leverage manual step is spot-checking the Django Admin Deal list at the QUALIFIED stage — before it burns a paid BetterContact credit — and marking obvious non-Chennai, junior-looking leads as wrong_fit.
04

What You Must Build/Configure Next

In order. Nothing here is optional if you want a live pipeline today.

  1. Generate three credentials before you touch the wizard

    The onboarding flow live-verifies each one on entry and will not let you proceed on a bad key — have all three ready first. Full breakdown in the Keys panel below.

  2. Clone and bootstrap locally

    Standard local install (not Docker) — make setup runs migrations and prepares the CRM tables in one shot. Exact commands in the Terminal panel.

  3. Create your Django admin superuser

    One-time account for /admin/ — this is where you'll review qualified leads and override wrong-fit matches the automated filters can't catch.

  4. Run the onboarding wizard end-to-end

    Six steps in fixed order: campaign → llm → mailbox → signature → bettercontact → account. Each step retries in place on a bad value — you cannot skip ahead with an unverified credential.

  5. Write campaign_target using the workaround from Section 03

    This is the single highest-leverage text you'll write in the whole setup — it's the only place age/tenure/city nuance can live at all. Template in the ICP Prompt panel.

  6. Start the daemon and watch the first burst

    manage.py rundaemon is the worker loop — leave it running, and check the Admin Deal list after the first 45–65 minute burst cycle completes.

  7. Set a manual QUALIFIED-stage review habit

    Not a command — a discipline. Since city/age can't be gated automatically, this is where you actually enforce "Chennai, 35–50" before a credit gets spent finding their email.
